# 11. 测试计划（D11）

## 11.1 目的与质量目标

用可重复、可审计的测试证明 D04 中的需求被满足，重点证明四件事：输出一定合法（NFR-COR-01）、分块不影响结果（NFR-COR-03）、快照单调（NFR-COR-04）、与成熟实现的行为差异可解释（NFR-COR-05）。

## 11.3 测试环境

- 固定并记录 MoonBit 工具链版本、Node.js 版本、Python 版本、jsonrepair 与 json-repair 的版本号。
- 后端：js、wasm-gc、native（以 Spike S4 结果为准）。
- 所有随机测试使用固定种子，失败时输出种子与最小化后的输入。
- 语料经脚本转成含字符串字面量的 `.mbt` 数据文件（ADR-010），保证所有后端的测试都能读取。

每条用例包含：编号、输入、选项、期望文本、期望修复记录（修复码加偏移）。期望值需人工审阅后才可写入，禁止用程序输出直接覆盖期望。

| BR-05 | 8 | 有无语言标记、结尾围栏、围栏之后的文字、skip\_prose |
| BR-06 | 14 加 8 | 单引号、弯引号、内部引号；前瞻的各种后继字符 |
| BR-07 | 8 | 无引号键、数字键、重复键三种策略 |

| BR-09 | 16 | 尾逗号、前导逗号、连续逗号、缺逗号、缺冒号 |
| BR-10 | 14 | 各种大小写、Python 字面量、undefined、NaN 三种策略 |
| BR-11 | 20 | 加号、前导零、点号开头与结尾、不完整指数、大整数原文 |

## 11.5 属性与模糊测试（TC-P）

| 编号 | 属性 | 生成器 | 规模 |
| --- | --- | --- | --- |
| TC-P-01 | 若返回成功，输出文本能被 core 严格解析 | G1 对合法 JSON 做变异；G2 随机拼接 JSON 字母表中的 token；G3 随机 UTF-16 序列含孤立代理项 | 不少于 20 万例 |
| TC-P-02 | 对输出再次修复，文本相同且无修复记录 | 同上 | 不少于 10 万例 |
| TC-P-03 | 任意分块的最终文本、值、修复记录（含位置）、错误与一次性结果完全相同 | 切分方式包括逐码元、随机长度、专挑热点位置（转义中间、`\u` 中间、代理对中间、斜杠之后、字面量中间、围栏中间） | 不少于 10 万例 |
| TC-P-04 | 对输入的每个前缀，相邻前缀的快照满足偏序 | 合法 JSON 与瑕疵 JSON 的所有前缀 | 不少于 5 万个输入 |
| TC-P-05 | 合法 JSON 恒等：无修复记录，值与 core 解析一致 | 随机合法 JSON：深度、大小可控，含转义、Unicode、大数、空容器 | 不少于 10 万例 |
| TC-P-06 | 任意输入与任意选项下，只会成功或抛出已声明的 E 码，不崩溃，不出现内部 E030 | 随机字节串（有损解码）、对合法 JSON 做删除、插入、替换、重复、截断变异 | 不少于 10 万例 |
| TC-P-07 | 超限输入得到 E020、E021、E022，且耗时不超过固定上限 | 深度 513 至 100 万的嵌套、超长字符串、超长输入 | 各 10 例以上 |

偏序函数 `leq(a, b)` 放在 testkit 中，自身先有单元测试；失败的输入由简单的删段式缩减器缩小后存入回归语料。

## 11.6 流式用例（TC-S）

- TC-S-01：D04 FR-09 的验收示例。
- 表驱动：D05 5.4 的每一行，分别检查快照与 `finish` 两种结果。
- TC-S-CHUNK：逐码元、逐字节喂入，与一次性结果对比。
- TC-S-UTF8：含中文、emoji 的输入按每个字节切分；非法 UTF-8 触发 E040。
- 生命周期：`finish` 之后再 `feed`、`finish` 之后再 `finish`、失败之后再调用，均得到 E030。
- TC-S-EVT：事件重放得到同一棵树（若实现 FR-16）。

## 11.8 差分测试（TC-D）

**流程**

1. 收集输入：（a）自编黄金用例的输入；（b）从参照库公开测试中摘录并标注来源与许可证（核对通过才可使用，RSK-09）；（c）自动变异语料，数千条。
2. 在 Node 上用 jsonrepair、在 Python 上用 json-repair 生成期望，记录输出或异常。
3. 脚本把输入与期望转成 `.mbt` 数据文件并提交，同时记录参照库与运行时版本。
4. MoonBit 测试逐条运行并比对**解析后的 JSON 值**是否相等，而不是比较文本。
5. 对不相等的用例分类并记入 `docs/DIVERGENCES.md`。

**分类**

| 类别 | 含义 | 处理 |
| --- | --- | --- |
| Equal | 值相等 | 计入等价 |
| DiffIntentional | 设计上有意不同（如快照策略、孤立代理项） | 写明理由与对应的 BR |
| DiffBug | 本库缺陷 | 修复并加回归用例 |
| OutOfScope | 参照库做了范围外的猜测式修复 | 说明并排除 |
| RefError | 参照库自身报错或不稳定 | 排除并说明 |

**指标**：等价率 = Equal 除以（总数减 OutOfScope 减 RefError）。目标：整体不低于 90%，P0 规则用例中除 DiffIntentional 外 100% 等价。参照库的版本变化可能影响结果，因此语料与期望随版本冻结后提交。

分歧记录模板：编号、输入（过长则截断）、本库输出、参照输出、类别、理由、关联规则。参照库只用于行为对照，不复制其源码。

## 11.9 跨后端与确定性（TC-X）

- TC-X-01：同一份合规语料（TC-G、TC-S 与抽样差分用例）在 js、wasm-gc、native 上运行，各自输出「用例编号与输出哈希」，脚本对比，必须完全一致。
- TC-X-02：同一后端上对同一输入重复运行三次，输出一致。

## 11.10 基准（TC-B）

数据集：合法 JSON（1 KB、100 KB、10 MB）、重度瑕疵 JSON、深嵌套（深度 500）、超长字符串（10 MB）。

| 编号 | 内容 | 方法 |
| --- | --- | --- |
| TC-B-01 | 线性性 | n、2n、4n 三个规模，耗时比不超过 2.3 倍 |
| TC-B-02 | 吞吐 | native 与 js 各跑五次取中位数，单位 MB/s |
| TC-B-03 | 流式开销 | 同一 1 MB 输入按 1 字节、16 字节、1 KB、64 KB 分块；再比较「每块取快照」与「只在最后取」 |
| TC-B-04 | 内存 | native 峰值内存，或可行的估算方法 |
| TC-B-05 | 产物体积 | wasm-gc release 产物大小 |

结果写入 `docs/BENCHMARK.md`：环境、方法、结果、与 jsonrepair（Node）的参考对比。对比只作参考，不作承诺；未达到 NFR 中「初定」目标时，如实披露并回写目标值。
