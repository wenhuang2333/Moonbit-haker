## 1.2 背景与问题

LLM 流式输出结构化 JSON 时有三个典型困难：

1. 中途只能拿到前缀，应用想边收边渲染，严格解析器会直接报错。
2. 模型输出常带瑕疵：markdown 代码围栏、单引号、尾逗号、注释、Python 风格字面量，或因 max\_tokens 被截断。
3. 失败时应用需要兜底，而不是整个请求作废。

TypeScript 和 Python 生态已有 jsonrepair、json-repair 等库。MoonBit 生态中我检索到的相关结果里，没有发现同类库，但检索并不完整【待核实：开工前必须在 mooncakes.io 与 GitHub 查重，见 D02】。MoonBit 已有 MCP 服务端 SDK 等 AI 工具链项目，解析 LLM 输出是其自然的配套需求。

## 1.3 项目目标

| 编号 | 目标 | 可度量指标 |
| --- | --- | --- |
| G1 | 一次性修复：任意字符串转为合法 JSON 文本，并给出修复报告 | P0 规则语料通过率 100% |
| G2 | 流式部分解析：分块输入，随时取快照 | 任意分块下最终结果与一次性修复一致，随机属性测试不少于 10 万例 |
| G3 | 可信：与成熟实现做差分测试 | 范围内用例与 jsonrepair 语义等价率不低于 90%，其余分歧 100% 分类记录 |
| G4 | 跨后端一致 | js、wasm-gc、native 在合规语料上输出逐字节一致 |
| G5 | 满足赛事验收 | 公开仓库、持续提交、README、测试、可复现演示、发布 mooncakes.io v0.1.0 |

## 1.4 范围

**范围内**：一次性修复；流式部分解析与快照；诊断报告；严格与宽松模式；资源限制；命令行工具；浏览器演示页；差分、属性、模糊测试；中英文 README。

**范围外**：语义级修复（猜测缺失字段的值）；完整的 JSON5 或 YAML 解析器；Schema 校验；复杂的格式化与美化（仅提供缩进选项）；网络与文件 IO（核心库不含）；对 jsonrepair 行为的逐条克隆。

## 1.5 目标用户与场景

| 用户 | 场景 |
| --- | --- |
| U1 AI 应用开发者（通过 js 后端用于 Node 或浏览器） | S1 修复 LLM 工具调用参数；S2 流式 UI 逐步渲染结构化输出 |
| U2 MoonBit 开发者 | S3 在 MCP 服务端、Agent 框架中解析模型输出 |
| U3 命令行用户 | S4 清洗日志或配置里的松散 JSON：管道输入输出 |

## 1.6 价值主张与差异化

1. 单一引擎同时支撑一次性修复与流式解析，两条路径行为一致，由分块不变性测试保证。
2. 公开差分测试报告：与 jsonrepair 的每一处分歧都有分类与理由。
3. 无递归、无正则的显式栈状态机：深层嵌套不会栈溢出，复杂度线性，并带资源限制。
4. 修复可审计：每一次修改都有带位置的诊断记录，且支持严格模式。
5. 多后端一致，并提供浏览器演示。
