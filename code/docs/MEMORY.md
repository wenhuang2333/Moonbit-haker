## 四、这张表能回答什么，不能回答什么

能回答：**同一份文档、同一个「读入 + 建树 + 保留」工作负载**下，各模式的峰值差多少，以及 InterJSON 与调用方本来就会用的两个运行时相比是高还是低。

不能回答：MoonBit **core** 的 `@json.parse` 单独占多少。core 没有文件读取入口，本库也刻意不暴露一个。能测到的最接近的两臂是 `--check`（建树、不渲染，本次 97.3 MB）与 `repair()`（建树并渲染，本次 171.6 MB）：`--check` 现在设置 `want_text=false`，所以两者之差是**渲染输出**的边际成本；剩下的 97.3 MB 是值树与字符串 parts，core 自身在这部分里占多少，从这两个数里拆不出来。要一个精确的 core 基线，需要给基准程序加一个 FFI 读文件入口（core 自身没有文件读取 API）。

默认的 `repair` / `--check` 主路径按 64 KiB `fread` 分块，每块直接 `feed_bytes` 给解析器，不把整份输入读成第二个 `String`；`explain`、`readiness`、`batch` 与 `llm` 仍然 `read_all`，所以这些臂的峰值还包含整份输入文本。主路径保留 1 MiB 前缀用于错误摘录，分块本身不保留。`streaming feed`、`readiness`、`llm --text` 三行之间以及它们与 `repair` 之间的差额，是计划、事件表与渲染输出的**边际**成本，而不是「流式模式省掉了值树」的证据。

另外，Python 一行的备注给出 `tracemalloc` 峰值：它是 Python **自身分配**的精确值，与 RSS 的差额是解释器与 GC 的空闲内存。把这个差值当成「实现效率」是不对的，这也是为什么同一张表里既给 RSS 也给 tracemalloc。

## 五、长文本形状：单条字符串吃掉整篇文档（TC-B-11）

上面四节用的是对象数组：成本主要是**值树**。LLM 场景里另一种形状同样常见——模型写文件、写 markdown 回答、写译文时，参数里几乎只有一个超长字符串，此时值树只有两个节点，成本几乎全是**字符串缓冲**。这一节用同样的字节量测这种形状：`{"text":"中文内容…"}`，13579079 B（12.95 MB，4526367 个码元）。

| 模式 | 峰值 RSS | 相对输入 |
| --- | --- | --- |
| --check（建树、不渲染） | 47.0 MB | 3.6 × |
| repair（渲染输出） | 55.1 MB | 4.3 × |

1.3.0 改动的是这一形状的成本结构，不是结果：字节入口 `feed_bytes` 过去只批量纯 ASCII 段，非 ASCII 字节一个码元一次 `parts.push(c.to_string())`，于是长文本文档的峰值随**字符数**而不是字节数增长。现在完整的 UTF-8 序列并成一次 run，一条 25 171 907 字节、8 388 619 码元的 CJK 文档实测由 239 075 328 B（228.0 MB，9.5 ×）降到 46–54 MB（1.9–2.2 ×，`--check`；峰值 RSS 随调用上下文抖动约 8 MB），`repair` 由 289 521 664 B（276.1 MB）降到 89.8–94.3 MB。那两个「修复前」数字**不是本次运行测的**——当前二进制已经修好——是同一批文件用改动前的二进制测出来的，记录在 `docs/BENCHMARK.md`「长文本输入」。

同一尺寸下两种形状可以直接比：13579171 B 的对象数组 `--check` 是 97.3 MB（7.5 ×，见第一节），同字节量的长文本 `--check` 是 47.0 MB（3.6 ×）——长文本省下的是值树，留下的是两份 UTF-16 文本（`parts` 与 `Json::string`）。但这个比值也不要与 25 MB 文件的 1.9–2.2 × 直接对比：峰值里有一部分与输入大小无关（运行时本身、主路径保留的 1 MiB 错误摘录前缀），它在较小的文档里占比更大。


`repair` 与 `--check` 之差是渲染输出的边际成本：长文本下它是整整第二份文本，所以这一形状的 `repair` 峰值明显高于 `--check`，与对象数组形状的结论一致。
