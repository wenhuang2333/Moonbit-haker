**2 of 95 `y_*` files get 2 repair record(s) in total.** Each one is listed here
with the record, its declared exactness, the `--check` status and the
`--for-execution` verdict:

| file | input | repair record | exactness | `--check` | `--for-execution` |
| --- | --- | --- | --- | --- | --- |
| `y_object_duplicated_key.json` | `{"a":"b","a":"c"}` | `R018 1:10 duplicate key merged` | lossy | 1 | refuse (5 E010) |
| `y_object_duplicated_key_and_value.json` | `{"a":"b","a":"b"}` | `R018 1:10 duplicate key merged` | cosmetic | 1 | accept (0) |

Every record is `R018 MergeDuplicateKey`. Both files are duplicate-key objects;
RFC 8259 permits duplicate names, so the input is valid JSON and JSONTestSuite
is right to list it under `y_`. JSONMend's default duplicate-key policy still
drops a member and records `R018`, and that record is what the false-repair count
measures. The distinction matters and is not hidden by the number: the record is
honest about the drop, and the exactness it declares separates the two files —
where the dropped and kept values differ it is `lossy` and the execution gate
refuses the document, where they are identical it is `cosmetic` and the gate
accepts it. So the repair machinery behaves as documented; the corpus simply
contains valid documents whose repair is optional rather than necessary.

### Valid `y_` files an oracle refuses

This is the direction worth recording: on this corpus JSONMend is the only

| file | input | `json_repair` | `jsonrepair` | oracle note |
| --- | --- | --- | --- | --- |
| `y_structure_string_empty.json` | `""` | reject | accept | repaired text is not JSON |

The one case is `y_structure_string_empty.json`, whose whole content is `""`.
`json_repair.repair_json('""')` returns the empty string — not a JSON
document — so the text-in/text-out/parse round trip this harness uses (the
same one `oracle_node.mjs` and `run_ambiguity.py` use) fails. Its object API
`json_repair.loads('""')` returns the empty Python string, which is correct,
so this is an artifact of the text API and not a parsing failure. It is
recorded rather than patched, because patching it would mean scoring the
Python oracle by a different rule than the Node one.

## What this does and does not prove

- **The corpus is independent; the harness and the reading are not.** The 318 test
  files were written by a third party (Nicolas Seriot) to test JSON parsers in
  general, and they are vendored verbatim at the commit above. The script that runs
  them, the choice of strict oracle, the accept/repair/reject classification and this
  analysis are ours, so a mistake in any of those is our mistake and the corpus being
  external would not catch it.
- **It tests syntax acceptance, not repair quality.** A `y_` file that needs no repair
  and an `n_` file that gets one are the only claims made. The corpus has no ground
  truth for what an invalid document *should* become, so "165 of 188 `n_` files
  repaired" measures how often JSONMend invents a value, not how often it invents
  the *right* value. It is not a substitute for `run_eval.py`, which scores recovered
  values against generated truth.
- **It is not a substitute for recorded real provider streams.** These are synthetic,
  hand-written edge cases. Real model output arrives as tool-call deltas with prose,
  truncation and retries; LLM_EVENTS.md and the recorded fixtures cover that, and this
  corpus says nothing about it.
- **The two oracles are repair libraries, not truth.** `json_repair` and `jsonrepair`
  appear here as *other implementations*. On `n_` files their willingness to return a
  value is evidence about them, and it cannot be used to argue that JSONMend is wrong
  when it accepts the same file.
- **What would move the headline.** If a later run reports 0 false repairs on `y_`,
  duplicate-key handling changed. The number is measured per run and the corpus
  fingerprint above fixes which files were measured.
